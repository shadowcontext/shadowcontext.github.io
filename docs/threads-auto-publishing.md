# Threads automatic publishing

ShadowContext can publish newly added Jekyll posts to Threads through Meta's
official Threads API. The integration is Threads-only and does not use Grok or
another AI provider.

## Repository publishing model

- The site is generated by Jekyll.
- Published posts are Markdown files under `_posts/` using the
  `YYYY-MM-DD-slug.md` filename format.
- `_config.yml` defines `url: "https://shadowcontext.com"` and
  `permalink: /:title/`, so a file such as
  `_posts/2026-07-22-example-post.md` has the canonical URL
  `https://shadowcontext.com/example-post/` unless its front matter overrides
  `permalink` or `slug`.
- Netlify CMS uses `publish_mode: editorial_workflow`; unpublished CMS entries
  are not added to `_posts/` on the publishing branch. Jekyll-style `_drafts/`
  paths, `draft: true`, and `published: false` are also treated as drafts by the
  automation.
- Posts with a future front-matter or filename date are skipped. Set
  `social_publish: false` in front matter to opt out an otherwise published
  post. The site's standing editorial safety rule also excludes breach-related
  content from automatic social publishing.

## Required GitHub secrets

Add these repository Actions secrets under **Settings → Secrets and variables
→ Actions**:

- `THREADS_USER_ID`: the Threads user ID that will own published posts.
- `THREADS_ACCESS_TOKEN`: a Threads user access token for that user.

The script reads both credentials only from environment variables. It never
prints either credential or an authorization header.

## Meta app setup and permissions

Create a Meta app with the Threads use case, authorize the target Threads user,
and grant the token:

- `threads_basic`
- `threads_content_publish`

The app may require Meta App Review before it can publish for Threads accounts
that do not have an app role. Confirm the token's user, scopes, and expiration
with Meta's Access Token Debugger before enabling real publishing.

## Manual dry run

Open **Actions → Publish New Posts to Threads → Run workflow** and provide a
title, optional description, and canonical URL. Leave **dry_run** enabled. The
workflow prints the exact final Threads text and makes no Threads API request.
Dry runs do not require the two repository secrets.

The same check can be run locally without credentials:

```sh
node automation/threads/publish-to-threads.mjs --dry-run \
  --title "Test security analysis" \
  --description "A short test summary." \
  --url "https://shadowcontext.com/test-security-analysis/"
```

## Real manual test

After configuring both secrets and verifying the Meta permissions, run the
manual workflow with **dry_run** disabled. This creates a real Threads post.
Use a clearly labeled test title and URL, and review the dry-run output first.

## Automatic publishing

The workflow runs on pushes to `main` that touch `_posts/**`. It compares the
push's before and after commits and processes only newly added Markdown files.
For each added post it:

1. Parses the title and the first available `description`, `summary`, or
   `excerpt` field.
2. Applies the site's Jekyll URL and permalink settings.
3. Skips drafts, unpublished posts, future-dated posts,
   `social_publish: false` posts, and breach-related content.
4. Truncates text to Threads' 500-character limit while retaining the complete
   canonical article URL.
5. Creates a text container and publishes it through the official Threads API.

Pull requests do not run the workflow. Concurrency protection queues overlapping
publishing runs instead of allowing them to post simultaneously.

Run the implementation checks locally with:

```sh
npm run lint:threads
npm run test:threads
```

## Token expiration

Meta long-lived Threads user tokens currently report a lifetime of about 60
days. Refresh a long-lived token while it is still valid, then update
`THREADS_ACCESS_TOKEN` if its value changes. Expired or revoked tokens cause the
publishing job to fail; the workflow does not perform token refreshes because
that would require storing the Meta app secret as an additional credential.

## Duplicate-post risk

GitHub's **Re-run jobs** feature replays the original push event. A successful
automatic publishing job that is rerun can therefore publish the same articles
again. Do not rerun a successful real publishing job. Use a manual dry run for
diagnostics, and delete an accidental duplicate directly in Threads if needed.
